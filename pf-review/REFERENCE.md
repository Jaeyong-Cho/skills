# pf-review Reference

## Execution Trace Map

Print before walking hops:

```
Entry point (file:line)
  → Aspect 1 (file:line)
  → Aspect 2 (file:line)
  → Object method (file:line)
  → ...
  → Response / side effect (file:line)
```

---

## Scenario List Format

Group by type before running:

```
Happy path:
  [ ] <normal scenario>
  [ ] ...

Edge cases:
  [ ] <boundary input>
  [ ] <concurrent access>
  [ ] ...

Error cases:
  [ ] <DB unavailable>
  [ ] <malformed input>
  [ ] ...
```

---

## Scenario HTML Report

Read `../pfj-grill/kanagawa.css`. Embed verbatim in `<style>` tag. Write all content in caveman style — follow `../caveman/SKILL.md`. All diagrams: inline `<canvas>` or pure CSS/SVG, no libraries.

Always include: scenario results table (name, type, Pass/Fail/Partial/Untestable, one-line finding), pass-rate progress bar per type, execution flow diagram for each failed scenario with failure point highlighted.
Include when warrants: issue map by layer (node-edge), coverage gaps with reason.

Footer: `Generated by pf-review · date · adr-slug`

---

## Doc File Formats

One file per entity per layer. Write in present tense — what **is**, not what was decided.

**`value/<N>-<entry-point>.md`** — the user need this entry point serves: what it does, what success looks like, what must never happen.

**`aspect/<N>-<concern>.md`** — how this concern is handled: algorithm or workflow, which objects it uses and from what angle. Mermaid diagrams for flows.

**`object/<N>-<entity>.md`** — full entity identity: properties, actions, behaviors, relationships, invariants. Mermaid diagrams for relationships.

Each file ends with a **Related files** section listing source and test files for that entity.
