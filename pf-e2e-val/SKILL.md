---
name: pf-e2e-val
description: |
  Create or edit E2E validation cases for a feature or concern — grills the user first to understand the code behavior, scaffolds/edits cases, runs the affected case(s) only, and generates a report about what was created or changed.
  Use when the user has a feature or concern to validate with real data. Triggers: "pf-e2e-val", "add E2E for this", "create validation", "validate this feature", "e2e this concern", "update validation", "edit E2E cases", or any request to set up or manage E2E testing for a feature.
  To re-run all existing cases use pf-e2e-val-report instead.
---

Check journal: `[ -n "$PFJ_PATH" ] && cat "$PFJ_PATH/today.md" 2>/dev/null`
For layer definitions read `../pf/references/layers.md`.

# VAO E2E Validation

```
validate/<slug>/
  cases/
    01-<name>/
      run.py        ← standalone: python run.py
      input.json
      expected.json
      result.json   ← written by run.py after execution
```

## Step 1: Understand concern + derive slug

Read user's concern or feature description. Derive slug (lowercase, hyphens, max 40 chars).

## Step 2: Grill

Find relevant source files: `grep -rn "<keyword>" src/ 2>/dev/null`

Read them. Understand entry points, inputs, outputs, error paths. Source code is truth.

Run `grill-me` skill.

## Step 3: Decide action

After grill concludes, infer from full context:

- **Create** — no scaffold exists, or user wants new cases → Step 4
- **Edit** — scaffold exists, user wants to fix/update specific case → Step 5
- **Remove** — delete case dir, done
- **Run only** — tell user to use `pf-e2e-val-report`; stop

If ambiguous, ask one plain-text question.

## Step 4: Derive + scaffold cases

Derive all cases. Number sequentially: `01-<name> [happy]`, `02-<name> [edge]`, `03-<name> [error]`, …

Show list. Ask via `AskUserQuestion`: "Add or remove any cases?" — adjust before scaffolding.

`mkdir -p validate/<slug>/cases`

For each case create `validate/<slug>/cases/<N>-<name>/`:
- **`input.json`** — sample input derived from case description
- **`expected.json`** — expected output derived from code behavior
- **`run.py`** — use `templates/run.py`; replace `<name>`, `<N>-<name>` placeholders; fill feature call under `# TODO`

## Step 5: Edit case

`ls validate/<slug>/cases/`

Ask via `AskUserQuestion` which case to edit. Open its `run.py`, `input.json`, `expected.json`. Apply changes from grill conclusions.

## Step 6: Run affected case(s)

For each case just created or edited:

```bash
cd validate/<slug>/cases/<N>-<name>
python run.py
```

Print stdout. Note pass or fail per case.

Ask via `AskUserQuestion`: "Generate the HTML report?" — if no, skip and stop.

## Step 7: HTML report

Follow `../pf/references/report.md` for structure, styling, and generation rules.

Report covers only this session's cases. Read their `result.json` files.

Save: `.pf/reports/validate/YYYY/MM-DD-<slug>.html`
Header: `e2e-val: <slug>` · date · action (created/edited) · one-line outcome.
Footer: `Generated by pf-e2e-val · date · slug`

Always include: cases-changed table (name, type, action, pass/fail, last log line), actual vs expected diff for failures, coverage note per case.
Include when warrants: failure analysis with source location, coverage map for gaps.

```
Report: .pf/reports/validate/YYYY/MM-DD-<slug>.html
```
