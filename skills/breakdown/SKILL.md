# Breakdown

Decompose one goal at a time into a tree, one full depth at a time — a **round**. A round applies steps 2-4 to every open node at the current depth before any of them goes a level deeper, so the tree grows breadth-first, depth by depth, top-down from the root. After a round finishes, show its slice — every node the round just produced, under its parent, axis labeled — before starting the next round. This lets a bad axis or a lopsided split get caught at the depth it happened, instead of surfacing two rounds later buried in a full tree.

A node drops out of the round loop the moment it passes the atomic test (step 4) — it becomes a leaf and stops descending, even while its siblings continue into further rounds. Rounds end when every open node is atomic.

1. **State the node as an outcome, not an activity** — the state of the world that exists when it's done, not the work you'll be doing. If the input goal is too vague to state that way ("improve onboarding"), rewrite it as a concrete, verifiable outcome before splitting it; ask the user if you genuinely can't tell what "done" means from context.

2. **Pick exactly one decomposition axis for this round**, applied to every open node at the current depth, and name it before listing children. Common axes: sequence (phases/stages the work passes through), component (parts of the system or deliverable), actor (who does the work), case (segments, scenarios, or conditions the goal must cover). Mixing axes within one round is the single most common way a split stops being mutually exclusive — a "by phase" child sitting next to a "by team" child will always overlap somewhere.

   **Build/feature goal:** when the node being split is to implement a feature (the outcome is working code), don't pick freely — walk the architecture stack top-down, outer to inner, one layer per round: **entrypoint** (round 1 — how the feature gets triggered: CLI, HTTP, event) → **UI** (round 2 — the user-facing surface, if the feature has one) → **handler** (round 3 — the Usecase layer: orchestrating the user goal) → **logic** (round 4 — the Logics layer: domain computation) → **objects** (round 5 — the Objects layer: domain state/data). This is the same stack `../references/archi.md` defines, walked from caller inward instead of by its dependency rule. Skip a round only if the feature genuinely has no node at that layer (e.g. no UI for a background job) — don't insert a placeholder child for it.

3. **Split along that axis, then test the split for MECE against the parent:**
   - *Mutually exclusive* — for any piece of work, exactly one child owns it. If you can't say which child a task belongs to, the children overlap; merge them or repick the axis.
   - *Collectively exhaustive* — the children, summed, fully reconstitute the parent. Ask "what's left over once every child is done?" — anything left over is a missing child, not an acceptable gap.

4. **Test each child for atomic.** A node is atomic when it's describable without "and", has one owner, and produces one deliverable. A node that still bundles more than one outcome, or that a single person can't finish in one sitting, is not a leaf yet — it carries into the next round, where step 2 picks it a fresh axis (or the next fixed layer, for a build/feature goal) and keeps splitting until it is.

5. **Show the round's slice.** Once every open node at this depth has been split (steps 2-4), present just this round: the axis used, and every child produced, nested under its parent. Nodes that hit atomic this round are marked as leaves; the rest carry into the next round. Then continue to the next round for whatever's left open — don't pre-compute deeper rounds before showing this one.

6. **Rewrite every atomic leaf as actionable: verb + concrete object + done condition.** Reject vague verbs with no observable end-state ("support", "improve", "explore", "handle") — replace each with the concrete action it was standing in for. A leaf that can't be pinned to a done condition isn't atomic yet; send it back through step 4. Read `../references/good-harness.md` and pick a concrete check per its axes for each done condition — if nothing in its harness table produces a check, the condition isn't stated concretely enough yet.

7. **Order the leaves.** Once every branch has bottomed out (no more open nodes), for every pair of leaves ask whether one must finish before the other can start (it consumes something the other produces, or needs a state the other creates) — record only real dependencies, not the order they happen to appear in the tree. Topologically sort on those dependencies: a leaf with no unresolved dependency is ready to schedule next. Leaves with no dependency between them are parallelizable — mark them as such side by side rather than inventing a sequence between them. From that same dependency graph, trace the **critical path** — the longest chain of hard dependencies from a leaf with none to a leaf everything downstream waits on — and flag the leaf on it most exposed to slipping (highest fan-out of dependents, or the most uncertain scope), with the reason.

8. **Present the full tree**, assembled from the rounds already shown, indented by depth with the axis used at each depth labeled inline (e.g. `by phase:`, `by component:`, or `entrypoint:`/`UI:`/`handler:`/`logic:`/`objects:` for a build goal). Number top-level children in presentation order (`1`, `2`, …) and every leaf beneath each with a dotted id in traversal order (`1.1`, `1.2`, … under section 1), so leaves stay addressable outside the tree. Then the execution order from step 7 as a flat list of dotted ids, grouping parallelizable leaves under the same round number, followed by the critical path: the chain of ids it runs through and which one is most exposed to slipping.

Completion criterion: every leaf is atomic (no "and", one owner, one deliverable) and actionable (verb + object + done condition); every round's children pass both the mutually-exclusive and collectively-exhaustive tests against their parent; the axis used at each round is stated and each round's slice was shown before the next began; every leaf has a position in the dependency-ordered execution list or is marked parallelizable with the leaf(s) it's parallel to; every leaf carries a dotted id scoped to its top-level section; the critical path is named with its most slip-exposed leaf and why.
