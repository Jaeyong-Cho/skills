# Do-Plan

Turn a written plan into done work instead of leaving its action items unbuilt.

1. **Ask for the plan.** Ask the user for the plan file path — don't guess a directory or assume the most recent plan written in this session. Ask again if the answer is missing or doesn't point to a real file. Completion criterion: user has given a concrete path to an existing plan file, containing acceptance criteria and `- [ ]` action items.
2. **Execute each unchecked action item, in order.** Read `../references/testing-guidelines.md` before modifying tests. The plan's first action item creates the git worktree named in its Worktree line (`git worktree add {path} -b {branch}`); every action item after that runs with the worktree as the working directory, not the main checkout — `cd` there before implementing, stay there for the rest of this skill. Follow the plan's verification method for each changed behavior. Add or change a test only when it protects an important behavior, contract, edge case, or regression; use the lowest sufficient test level and avoid duplicate coverage. TDD is not mandatory, but for a bug fix, whenever practical reproduce the bug and add the failing regression test before fixing it. Run the focused planned test/check and confirm it passes before checking off the item (`- [x]`). Stop and ask the user if an item is ambiguous, its prerequisite failed, or its required verification cannot be run—don't silently substitute a heavier test.
   - **Assert on uncertainty.** If the item touches a function named in the plan's Assertions section, write that line's assert as a real runtime statement in the implementation code, at the exact point it checks (language-native `assert`/equivalent, not a comment, not test-only) — same rigor as Verification Method rows.
   - **Follow the abstraction level mark.** If the item carries an `[L1]`/`[L2]`/`[L3]` tag, read `../references/abstraction-levels.md` and write the function to that level's rule before checking it off: `[L1]` orchestrates only, delegates to the `[L2]` items below it, no L3 mechanism inline; `[L2]` holds the business rule, depends on L3 only through an interface, not a concrete implementation; `[L3]` is mechanism-only, no business decisions. An `[L1]` item whose listed `[L2]`/`[L3]` items don't exist yet — do those first, in order. Choose tests by the behavior and failure risk under `../references/testing-guidelines.md`, not mechanically by abstraction level.
   - **STOP before merging a branch or releasing** — these are human-invoked only, `@skills/do-plan` cannot run them. Leave the branch-merge/release item unchecked and **MUST ASK the human to confirm** before either happens; never merge or release on the agent's own judgment. Once the human confirms the merge happened, remove the worktree (`git worktree remove {path}`, `-f` only if the human confirms discarding uncommitted changes there) and run `git worktree prune` from the main checkout, then check the item off.
   - **Dogfood test.**

   Completion criterion: every action item in the plan is either `- [x]` or explicitly called out as blocked.
3. **Verify acceptance criteria.** Check each one against the real state of the repo and record pass/fail; do not assume from the diff alone. Run the row's Verification Method (per `../references/requirement-engineering.md`) at the selected level. If it names a test, confirm that test exists and passes; if it names another deterministic check, run that check and capture its result.
   - **Run `@skills/experiment` on High-uncertainty ground.** A row whose Assertions-section line is tagged High uncertainty gets more than a passing test: run `@skills/experiment` to see the actual implementation result for real (plan → act → analyze), and record its verdict and file path next to that row — a green test alone isn't trustworthy evidence there.
4. **Review, then commit — only after confirmation.** Run the plan's Build line and every test/check selected by the plan for real. If the build, any planned verification, or any acceptance criterion fails (step 3), don't commit — tell the user what's broken instead. Otherwise run the plan's code-review gate on the current worktree diff, requirement, design, changed files, and test evidence. Use the repository's review skill when one exists; otherwise run `@skills/thermo-nuclear-code-quality-review`. Also run `git diff --check`. Classify findings as blocking, accepted risk, or non-blocking. Resolve every blocking finding, rerun the affected focused/regression checks, and repeat the review until no blocker remains. If a fix changes observable behavior, return to the requirement/design approval gate instead of silently changing scope. Only then stage exactly the files this plan touched (never a blind `-A`/`.`; review what's staged first) and **STOP**: show the user the review result, staged files, and the plan's Commit line as the proposed message. **MUST ASK** the human to confirm before running the real `git commit` — never commit on the agent's own judgment. Only once confirmed, run the commit for real and note the resulting commit hash next to the Commit line in the plan file.
5. **Write the report.** Read `../references/document-style.md` first — its structure governs the draft: an Introduction (what plan, why run), a Body (each action item done vs. blocked, each acceptance criterion's pass/fail, with evidence, plus a plain-language "What changed" list — one line per action item, no jargon), and a Conclusion (overall outcome, next actions for anything blocked or failed). **Copy the plan's QA Procedure into the report as a "Try it yourself" checklist**, same order: run each step that doesn't need a human (state the actual observed result next to it), leave `- [ ]` for steps that genuinely need a human's eyes/hands (UI, physical device) so they know exactly what to click and what to expect. For any `- [ ]` step the human can run from a terminal (curl, CLI call, short script), give the exact copy-pasteable command inline in the checklist — if it takes more than one command, write it as a throwaway script next to the report (`{plan-file}.qa/{nn}-{slug}.sh` or equivalent), not into the repo, and reference its path in the checklist item, so the human runs one thing and sees the result themselves instead of reading code. Write it next to the plan file, as `{plan-file}.report.md`.

Completion criterion: every action item is checked or blocked, every acceptance criterion has a stated pass/fail, the code-review result and any residual risks are recorded, a commit hash is recorded (or a failing build/test/acceptance-criteria run, a blocking review finding, or a commit still awaiting the human's confirmation explains why not), and the report file exists reflecting all three.

Tell the user the report file path when done, and paste the "Try it yourself" QA Procedure checklist directly into the session (not just the file path) so the human can act on it without opening the file.
