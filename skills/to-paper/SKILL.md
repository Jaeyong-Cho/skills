# To-Paper

A research paper as one manifest.json plus a build script, the same split `@skills/diagram-design` uses between content and rendering. Everything the paper says lives in `manifest.json`; `index.html` is always regenerated from it, never hand-edited.

1. **Confirm the output directory.** **MUST ASK** the user where `{slug}-research-paper/` should be written before creating anything — never assume a path, even an obvious-looking one. Recommend `./{slug}-research-paper/` at the current project root as the default (this repo's usual "skill-named directory at project root" convention), but let them name any path. Once confirmed, `mkdir -p {dir}/assets`. Completion criterion: a confirmed absolute path from the user, directory created.
2. **Draft the manifest.** Read `MANIFEST-FORMAT.md` first for the exact JSON schema (seven fixed section keys, paragraph/subsection shape, `diagrams` array). Write `{dir}/manifest.json`. Subtitles on `background`/`methodology` subsections are optional — only split a section that genuinely has distinct parts. Where prose should point at a figure, write `{{fig:some-id}}` inline (e.g. "...as shown in {{fig:pipeline}}...") — it resolves to "Fig N" once that diagram exists; add or adjust these after step 4 picks each diagram's `id` if drafting prose first.
3. **Pick each figure's shape — table or diagram, independently each time.** Naturally rows and columns (a before/after comparison, a results breakdown)? Use `"type": "table"` in the manifest (`MANIFEST-FORMAT.md`) and skip straight to step 6 for that entry — no diagram-design involvement, no HTML draft, no SVG. Otherwise read `DIAGRAM-SELECTION.md` first — its "When to use a diagram at all" gate (if a table or a well-written sentence would teach the reader as much, don't draw it), its "Selection: semantic pattern, then visual type" table (route through a semantic pattern first when behavior/state/enforcement/risk carries the meaning, else pick a type directly), its Visual-type guide table (architecture, flowchart, sequence, timeline, quadrant, tree, layer stack, bar/line/scatter chart, ...), and its Rules of thumb — the dominant axis of what the figure shows decides the type, not habit. **MUST NOT** default to whatever type the last figure used — across all figures in the paper, at least 3 different kinds are required (step 7 lints this), so pick each one on its own merits.
4. **Draw at least 5 figures total** (tables count) **— each diagram as a full diagram-design HTML file, nothing more.** 5 is a floor, not a target; add more wherever step 3's gate says a reader would learn more from a picture or a table than a paragraph. For each non-table figure: read `../diagram-design/references/style-guide.md` and the `../diagram-design/references/type-*.md` matching its type from step 3. Also read the `../diagram-design/assets/example-*.html` for a target type, plus `DIAGRAM-AUTHORING.md` (kept local so this doesn't require loading diagram-design's much larger `SKILL.md`) for its Philosophy, Universal Anti-patterns, Design System (node-type → treatment table, typography spec), Core SVG Primitives, Layout & Spacing, and Summary Card Pattern where a figure calls for one — and author it the way `@skills/diagram-design` actually would: a complete, self-contained HTML file (its own `<head>` with the Google Fonts link, inline `<style>` using the `paper`/`ink`/`muted`/`accent`/`link` tokens **at their light-skin values only** — never the dark-skin column, since `assets/template.html`'s page background is fixed light and a dark-skinned figure would clash — the accessible `<svg role="img" aria-labelledby="...">` with `<title>`/`<desc>` as its first children, plus explicit `width`/`height` attributes matching its `viewBox`). **Do not invoke `@skills/diagram-design` directly** — read its methodology and reproduce it by hand; invoking it triggers its own style-guide-onboarding gate for what's here just one figure inside a paper. Save the draft as `{dir}/assets/{id}-{slug}.diagram.html` and **use it as the manifest's `file` directly** — don't run `../diagram-design/references/export.md`'s SVG export procedure. That procedure builds a fully standalone, portable `.svg` (XML declaration, escaped Google Fonts `@import`), which is real, avoidable cost for a figure that's only ever going to be embedded inside this one paper: `scripts/build_paper.py` extracts the `<svg>...</svg>` block straight out of the `.diagram.html` draft at build time and inlines it directly into `index.html` (no `<img>`, no second file, no export ceremony, and no staleness risk from forgetting to re-export after editing the draft). Only run `export.md` separately, by hand, if the user explicitly wants a standalone `.svg` of one figure to reuse outside this paper.
5. **Validate each draft.** Walk `DIAGRAM-AUTHORING.md`'s Pre-Output Checklist (Taste Gate) against it by hand first — it's the only place the Type fit / Remove test / Signal / Typography judgment calls live; nothing in this skill automates those. Then run its Technical items' automated counterpart, diagram-design's own validator (vendored into this skill so step 7's lint can call it too): `python3 scripts/self_check.py {dir}/assets/{id}-{slug}.diagram.html` — fix anything either flags before moving on. Catching it here is just faster feedback; step 7 re-runs self_check.py on every diagram regardless, so a skipped run here isn't a skipped check overall — the hand-walked checklist items are the part step 7 can't catch.
6. **Add every figure to the manifest's `diagrams` array** — `id`, `caption`, `section` (which can target a whole top-level section, one specific subsection, e.g. `"methodology.data-collection"`, or one specific paragraph of either, e.g. `"methodology.data-collection@2"`, per `MANIFEST-FORMAT.md`'s sub-title/paragraph granularity), plus either `diagram_type` (its exact "Use" name from step 3's Visual-type guide, e.g. `"Flowchart"`) + `file` (the `.diagram.html` draft, or a `.svg` if you have one already), or `rows`+`"type": "table"`. Where prose should point at one, use its `{{fig:some-id}}` placeholder from step 2.
7. **Lint the manifest.** Run `python3 scripts/lint_paper.py {dir}/manifest.json` (relative to this skill's directory). Fix every reported violation — title word count, abstract-is-one-paragraph, a per-section paragraph-count range (a subsection inherits its section's range) — introduction 3-5, background 4-8, methodology 2-4, results 2-4, discussion 3-6, conclusion 1-3, see `lint_paper.py`'s `SECTION_PARAGRAPH_RANGES` — 3-8 sentences per paragraph, at most 20 words per sentence, at most 140 characters per caption, at least 5 figures (each `file`'s `<svg>` block accessible with a `viewBox` and `width`/`height` that numerically match it, every rect/circle/ellipse/line inside that `viewBox` — the outermost `<svg>` clips by default, so a shape added without widening the `viewBox` to fit is cut off, not scaled — each table's rows uniform-width, and each file passing the vendored `scripts/self_check.py` diagram-safety/motion checks) using at least 3 different `diagram_type`/table kinds, every `{{fig:some-id}}` reference naming a real diagram — and re-run until clean. A red lint is not a done draft.
8. **Build `index.html`.** Run `python3 scripts/build_paper.py {dir}/manifest.json`. It renders `{dir}/index.html` from `assets/template.html`, deriving section numbers (Introduction=1 … Conclusion=6, subsections `N-1`, `N-2`...) and figure numbers (Fig 1, Fig 2... in reading order, resolving every `{{fig:some-id}}` to a link) itself — never hand-number a heading or figure in the manifest — and copies in an executable `{dir}/serve.sh` so the user can preview it (`cd {dir} && ./serve.sh` then open `http://localhost:4802`; browsers block a `file://` page's relative asset links, so opening `index.html` directly may not show everything).
9. **Re-run after any later edit.** A follow-up change to content or a diagram means editing `manifest.json` or the `.diagram.html` draft directly, then repeating steps 7-8 — never hand-editing `index.html`. Editing a draft never needs a separate re-export step; the next build picks it up.

Completion criterion: `manifest.json`, `index.html`, `serve.sh`, and at least 5 figures (`assets/*.diagram.html`/`*.svg` and/or table entries) exist; step 7's lint is clean; `index.html`'s headings show the numbering step 8 derived.

Tell the user the output directory path, that it's clean of lint errors, and the `cd {dir} && ./serve.sh` command to preview it, when done.
