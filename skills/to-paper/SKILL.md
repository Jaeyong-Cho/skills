# To-Paper

A research paper as one manifest.json plus a build script, the same split `@skills/diagram-design` uses between content and rendering. Everything the paper says lives in `manifest.json`; `index.html` is always regenerated from it, never hand-edited.

1. **Confirm the output directory.** **MUST ASK** the user where `{slug}-research-paper/` should be written before creating anything — never assume a path, even an obvious-looking one. Recommend `./{slug}-research-paper/` at the current project root as the default (this repo's usual "skill-named directory at project root" convention), but let them name any path. Once confirmed, `mkdir -p {dir}/assets`. Completion criterion: a confirmed absolute path from the user, directory created.
2. **Draft the manifest.** Read `MANIFEST-FORMAT.md` first for the exact JSON schema (six fixed section keys, paragraph/subsection shape, `diagrams` array). Write `{dir}/manifest.json`. Subtitles on `background`/`methodology` subsections are optional — only split a section that genuinely has distinct parts. Where prose should point at a figure, write `{{fig:some-id}}` inline (e.g. "...as shown in {{fig:pipeline}}...") — it resolves to "Fig N" once that diagram exists; add or adjust these after step 4 picks each diagram's `id` if drafting prose first.
3. **Pick each diagram's type.** Read `DIAGRAM-SELECTION.md` first — its "When to use a diagram at all" gate (if a table, a bulleted list, or a well-written sentence would teach the reader as much, don't draw it), its Visual-type guide table (architecture, flowchart, sequence, timeline, quadrant, tree, layer stack, bar/line/scatter chart, ...), and its Rules of thumb — the dominant axis of what the figure shows decides the type, not habit.
4. **Draw at least 5 diagrams.** 5 is a floor, not a target — more figures are good; add one wherever step 3's gate says a reader would learn more from a picture than a paragraph, don't stop once the floor is met. Read `../diagram-design/references/style-guide.md` (tokens: `paper`/`ink`/`muted`/`accent`/`link`, Instrument Serif / Geist / Geist Mono) and the `../diagram-design/references/type-*.md` matching each figure's type from step 3, and follow its §1 Philosophy and §4 anti-patterns. **Do not invoke `@skills/diagram-design` directly** — it renders a full standalone HTML document; this skill only needs the bare `<svg>...</svg>` markup, saved as its own file under `{dir}/assets/{id}-{slug}.svg`, using the same tokens as `assets/template.html` so figures and page match. Every SVG needs a `viewBox` (not just fixed `width`/`height` — without one, shrinking it to the page's `max-width` can crop it) and carries the accessible-SVG contract step 5's `scripts/lint_paper.py` checks — `role="img"`, a `<title>` as its first child, a non-empty `<title>`/`<desc>` pair with diagram-prefixed ids, `aria-labelledby` naming them in that order. Add each to the manifest's `diagrams` array (`id`, `file`, `caption`, `section`) — `section` can target a whole top-level section or one specific subsection (`"methodology.data-collection"`), per `MANIFEST-FORMAT.md`'s sub-title granularity.
5. **Lint the manifest.** Run `python3 scripts/lint_paper.py {dir}/manifest.json` (relative to this skill's directory). Fix every reported violation — title word count, abstract-is-one-paragraph, 3-8 paragraphs per other section/subsection, 3-8 sentences per paragraph, at most 20 words per sentence, at most 140 characters per caption, at least 5 diagrams with existing accessible SVG files carrying a `viewBox` (the same contract `diagram-design/scripts/self_check.py` enforces, applied to a bare `.svg` instead of a full HTML page), every `{{fig:some-id}}` reference naming a real diagram — and re-run until clean. A red lint is not a done draft.
6. **Build `index.html`.** Run `python3 scripts/build_paper.py {dir}/manifest.json`. It renders `{dir}/index.html` from `assets/template.html`, deriving section numbers (Introduction=1 … Conclusion=5, subsections `N-1`, `N-2`...) and figure numbers (Fig 1, Fig 2... in reading order, resolving every `{{fig:some-id}}` to a link) itself — never hand-number a heading or figure in the manifest — and copies in an executable `{dir}/serve.sh` so the user can preview it (`cd {dir} && ./serve.sh` then open `http://localhost:4802`; browsers block a `file://` page's relative `assets/*.svg` links, so opening `index.html` directly won't show the figures).
7. **Re-run after any later edit.** A follow-up change to content or figures means editing `manifest.json` (or replacing an SVG under `assets/`), then repeating steps 5-6 — never hand-editing `index.html`.

Completion criterion: `manifest.json`, `index.html`, `serve.sh`, and at least 5 `assets/*.svg` files exist; step 5's lint is clean; `index.html`'s headings show the numbering step 6 derived.

Tell the user the output directory path, that it's clean of lint errors, and the `cd {dir} && ./serve.sh` command to preview it, when done.
