# To-Plan

Turn decisions into a plan document instead of leaving them to evaporate at the end of the chat.
Write a handoff document summarising the current conversation so a fresh agent can continue the work.
**MUST** instruct the detailed step-by-step so a cheap agent model can run.
**MUST NOT** skip or abstract the action items.

1. **Determine the input.** Default to this session's settled decisions or a named target supplied by the user. If the target includes an approved requirement document and OOD design document from the full prototype → requirements → OOD workflow, treat those artifacts as authoritative and do not run another requirements interview. Otherwise, if the target is not settled, use the existing feature/fix or Story checklist before drafting; do not draft from assumptions. For the full workflow, the named target is exactly one approved vertical slice and its requirement/design documents. Completion criterion: the plan's scope is stated as either "this session" or a named target, never assumed silently.
2. **Follow document style.** Read `../references/document-style.md` first — its Introduction/Abstraction/Detailed structure and size limits govern the draft.
3. **Follow ponytail style.** Run `/ponytail` (Skill tool) over the action items — cut speculative scope, keep each item to the smallest change that works.
4. **Follow deep module.** Read `../references/deep-modules.md` first — follow this philosophy.
5. **Choose tests by confidence and cost.** Read `../references/testing-guidelines.md`. Plan only tests that protect important behavior or contracts at the lowest level that provides sufficient confidence; do not require TDD, a test per function, duplicate coverage, or every test level.
6. **Follow requirements engineering.** Read `../references/requirement-engineering.md` first — its Acceptance Criteria table (Given-When-Then, Category, Verification Method) is the format for step 8's Acceptance criteria below; Verification Method keeps each criterion traceable to an appropriate test or deterministic check.
7. **Follow ELI5.** Make the plan so a fresh cheapest model agent can understand it.
8. **Draft the plan**, covering:
   - Target project (e.g. path of the repo) and the exact requirement/design artifact paths for this slice.
   - Acceptance criteria — the slice's decisions as a table per `../references/requirement-engineering.md`; each row's Verification Method names the existing or planned test/check and its level (`unit`, `integration`, `API/contract`, `E2E`, or genuinely `manual`). Choose the smallest level that protects the behavior per `../references/testing-guidelines.md`; do not duplicate the same confidence across levels.
   - QA Procedure — one numbered, human-executable step per Acceptance criteria row, same order (precondition, exact steps to do, exact observable result to expect). No jargon — this is the doc a human with zero context uses to check the feature actually works.
   - Deferred items — one line per `TODO:`-tagged deferred item from the approved requirement/design context (empty if none).
   - Assertions — one line per point of uncertainty found in this session: name the function/file it belongs to, what it checks (precondition, invariant, or postcondition), its uncertainty tag (High/Low, per `../references/grill-impact.md`), and that it's a real runtime assert statement written directly in the implementation code at that point (`assert` in Python, `assert()`/`static_assert` in C++, etc.) — not a comment, not test-only. `@skills/do-plan` writes each line's assert as part of the action item that touches that function, and runs `@skills/experiment` on every High-tagged line instead of trusting the assert/test alone.
   - **MUST WAIT** To run code review in other session — name the review skill/command to run after implementation and validation but before commit. Use the repository's review skill when one exists; otherwise use `@skills/thermo-nuclear-code-quality-review`. The review must inspect the requirement, design, current diff, tests, and residual risks; `git diff --check` is also required.
   - Commit — draft the commit message now (why this change, not a file list); `@skills/do-plan` runs the real `git commit` with it only after every action item is checked, the build and planned tests/checks pass, acceptance criteria hold, and the code review has no blocking finding. Human confirmation is still required.
   - Release / Branch merge gate — **MUST CONFIRM** with the human before releasing or merging any branch. For the full multi-slice workflow, record this as a gate rather than an implementation action item; the coordinator handles aggregate merge/release after slice plans finish. Once a merge is confirmed, `@skills/do-plan` may remove the worktree named below and run `git worktree prune`.
   - Worktree — the branch named in the approved workflow context and the worktree path it gets (sibling to the repo: `../{repo-name}-{branch}`), e.g. `feature/x` at `../myrepo-feature-x`.
   - Build — the target project's build command (e.g. `npm run build`, `make`) and confirmation it currently passes; name only the relevant test commands selected under `../references/testing-guidelines.md` so `@skills/do-plan` can run them before committing.
   - Action items, each as `- [ ] {item}` — the first item **MUST** be creating the git worktree named above (`git worktree add {path} -b {branch}`), before any other action item runs; every later action item runs with that worktree as the working directory, not the main checkout. `@skills/do-plan` executes and checks these off in place.
     - **Abstraction level mark.** For an item that creates or changes a function/method, read `../references/abstraction-levels.md` and tag it with the level it belongs at: `- [ ] [L1] {item}` / `[L2]` / `[L3]`. For an `[L1]` item, also list the `[L2]`/`[L3]` functions it needs as their own action items (existing or new) — `L1 → L1 → L2` (nested orchestration) and `L1 → L3` (skipping L2 when no business rule applies) are both fine per that doc; an `[L1]` item skipping straight to `[L3]` is a smell only when a real business rule (validation, calculation, policy) is being skipped along with it, not by default. For every changed behavior, choose its Verification Method using `../references/testing-guidelines.md`; do not mechanically create a test for each `[L2]`/`[L3]` function.
   - Dogfood test.
9. **Write it.** **MUST ASK** confirmation of the directory first, per `../references/question-format.md`'s ❓/➡️ format — recommend the current directory (`./plans/`) as the default, unless the user asks to file it under the wiki instead, in which case read `../references/research-topic-directory.md` first and confirm `{NN}-{slug}` the same way; skip re-asking if already confirmed earlier this session. Once confirmed, write to `./plans/{nn}-{slug}.md` (creating `plans/` if needed) or `{NN}-{slug}/plans/{nn}-{slug}.md` under `~/wiki/today/research/`, whichever was confirmed — `{nn}` the next zero-padded sequence number inside `plans/` (count existing files there; starts at `01`).
10. **One slice per plan.** If the input contains more than one vertical slice, split it into `{nn}-{slice-slug}.md` files in the same `plans/` directory, one file per vertical slice — each file a complete, independently executable unit with its own requirement/design paths, acceptance criteria, QA Procedure, action items, review gate, and commit message. Do not split one slice into horizontal plans such as backend/frontend or domain/infrastructure.

Completion criterion: the file (or files, if split) exists; each file names exactly one vertical slice and its requirement/design paths; acceptance criteria, deterministic verification methods, code-review gate, and action items are present and traceable to the determined input; every action item is detailed enough for `@skills/do-plan` to execute without guessing. This plan document is the only artifact — no spec document is written.

Tell the user the file path(s), and that `@skills/do-plan` executes it, when done.
