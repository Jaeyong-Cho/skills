# VAO Validation — Run + Report

## Step 1: Resolve slug + cases to run

If user provides feature name or slug, use it. Otherwise:

```bash
ls validate/
```

List available slugs and ask which to run.

Verify scaffold exists:

```bash
ls validate/<slug>/cases/ 2>/dev/null
```

Missing → tell user to run `pf-e2e-val` first to scaffold.

**Determine scope:**

- User names specific case(s) → run only those
- User says "all" or "run all" → run all cases
- Otherwise → list cases and ask which to run:

```bash
ls validate/<slug>/cases/
```

---

## Step 2: Run

For each selected case (or all cases if "run all"):

```bash
cd validate/<slug>/cases/<N>-<name>
python run.py
```

Print stdout per case. Note pass or fail. Each `run.py` writes its own `result.json`.

Show final pass/fail count after all cases complete.

---

## Step 3: Rich HTML report

Follow `../pfj-grill/REPORT.md` for structure, styling, interactivity, and generation rules.

Read `result.json` for each case that was run.

Save: `.pf/reports/validate/YYYY/MM-DD-<slug>.html`

```bash
mkdir -p .pf/reports/validate/YYYY
```

Header: `e2e-val-run: <slug>` · date · scope (specific cases / all) · one-line outcome.
Footer: `Generated by pf-e2e-val-run · date · slug`

**Always include:**
- **Pass rate** — progress bar: passed / total for cases run, broken down by type (happy/edge/error)
- **Results table** — case name, type, status (pass/fail/warn), last log line
- **Failure analysis** — for each failed case: actual vs expected diff, log trace, likely cause

**Include when content warrants:**
- **Pattern analysis** — which layer (value/aspect/object) has most failures → where bug lives
- **Log patterns** — recurring messages across cases; signal vs noise
- **Coverage map** — scenarios covered vs missing; gaps to add next (only meaningful when all cases run)

Print path:
```
Report: .pf/reports/validate/YYYY/MM-DD-<slug>.html
```
